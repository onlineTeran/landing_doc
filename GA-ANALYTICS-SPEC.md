# GA-мітки: специфікація подій для продуктових аналітиків

> Призначення: готовий шаблон специфікації аналітики лендінгу (GA4-орієнтований), який (а) розробник
> заповнює під конкретну кампанію, (б) передається продуктовим аналітикам як контракт «що, коли і з
> якими параметрами відлітає», (в) синхронізований з конфігом CTA
> ([`CTA-AND-LINKS.md`](CTA-AND-LINKS.md)) за побудовою.

**Статус:** аналітика в референс-білді не реалізовувалась (**Спостережено**-геп) — увесь документ
**Рекомендовано**; після першого реального впровадження підняти мітки й зафіксувати уроки (MINOR).

---

## 1. Naming convention (GA4)

- Імена подій і параметрів — `snake_case`, лише латиниця; **ліміти GA4:** ім'я події ≤ 40 символів,
  ім'я параметра ≤ 40, значення параметра ≤ 100 символів, ≤ 25 параметрів на подію.
- Не перевизначати [автоматичні/рекомендовані події GA4](https://support.google.com/analytics/answer/9267735)
  (`page_view`, `session_start`, `click`…) — власні події лендінгу мають префікс домену кампанії
  через параметр, а не через ім'я (ім'я подій стабільне між кампаніями, кампанія — параметр).
- Один словник на всі лендінги: нові кампанії НЕ вигадують нові імена подій — лише нові значення
  параметрів (`landing_id`). Так звіти порівнянні між кампаніями без переналаштування.

## 2. Спільні параметри (на кожній події лендінгу)

| Параметр | Тип | Приклад | Звідки |
|---|---|---|---|
| `landing_id` | string | `spring_launch_2026` | константа з config |
| `landing_version` | string | `1.4.0` | версія білда/тег |
| `embed_mode` | string | `iframe` \| `full_page` \| `standalone` | визначається в рантаймі |
| `locale` | string | `uk` | `IframeBridge.config.locale` або дефолт |
| `theme` | string | `dark` | `IframeBridge.config.theme` або дефолт |
| `has_auth` | boolean | `true` | `IframeBridge.config.hasAuth` (НЕ token, лише прапорець) |

**Ніколи не передавати:** token, будь-які PII (email, телефон, id користувача) — user-ідентифікація
живе на боці продукту.

## 3. Таксономія подій (словник)

| Подія | Коли відлітає | Параметри (крім спільних) | Власник |
|---|---|---|---|
| `landing_view` | Перший рендер лендінгу (раз на перегляд) | — | лендінг |
| `section_view` | Секція вперше ≥50% у viewport (IO, раз на секцію) | `section_id` (hero/steps/map/faq/promos…) | лендінг |
| `scroll_depth` | Пороги 25/50/75/100% (раз на поріг) | `depth` (number) | лендінг |
| `cta_click` | Клік будь-якої CTA | `cta_id` (= `analyticsId` з config/actions.ts), `action_kind` (external/product/event_action/anchor) | лендінг |
| `video_start` | Перший старт відтворення hero/сценового відео | `video_id` | лендінг |
| `video_complete` | Відео дограло до кінця (для loop — перший повний цикл) | `video_id` | лендінг |
| `faq_open` | Розкриття FAQ-питання | `question_id` (index/slug) | лендінг |
| `iframe_ready` | `IframeBridge.init()` виконано, `loaded` надіслано | — | лендінг |
| `integration_error` | Ядро недоступне / origin поза whitelist / контракт зламався | `error_code` | лендінг |
| `page_view` | — | — | **лише продукт** (лендінг НЕ шле) |

Правило дедуплікації: **кожна подія має рівно одного власника.** Лендінг ніколи не шле `page_view`
(його шле продуктовий контейнер); продукт ніколи не дублює події зі словника лендінгу. Якщо продукт
хоче трекати факт відкриття лендінгу — він робить це своєю подією на своєму боці.

## 4. Канал доставки залежить від режиму вбудовування

| Режим | Канал | Деталі |
|---|---|---|
| **Full-page embed** | `dataLayer` продукту | Лендінг на домені продукту → GA продукту вже на сторінці. Лендінг лише пушить: `window.dataLayer?.push({ event: 'cta_click', ...params })`. Власний GA-property НЕ створювати. |
| **Iframe embed** | узгодити з командою продукту | Iframe — third-party контекст: власний GA всередині обмежений (cookies/consent). Правильний шлях — переслати подію батькові. У чинному контракті (`IFRAME-BRIDGE-INTEGRATION.md`) є лише `event_action`; чи допустимо слати аналітику через нього, чи потрібен окремий тип повідомлення (напр. `analytics_event`) — **питання до розробників батьківського застосунку** (за контрактом нові типи додаються на їхньому боці). Це пункт Discovery. |
| **Standalone** (прев'ю/шеринг) | власний gtag або нічого | Якщо потрібно — окремий GA-property лише для standalone; не змішувати з продуктовими даними. |

**Виведено:** через це аналітичний шар лендінгу має бути **адаптером** — компоненти викликають один
`track()`, а канал обирається в рантаймі:

```ts
// composables/useAnalytics.ts (скетч адаптера)
export function useAnalytics() {
  const common = { landing_id: LANDING_ID, landing_version: VERSION, /* embed_mode, locale, theme, has_auth */ }

  function track(event: string, params: Record<string, string | number | boolean> = {}) {
    const payload = { ...common, ...params }
    if (window.dataLayer) window.dataLayer.push({ event, ...payload })            // full-page
    else if (window.IframeBridge && window.self !== window.top)
      window.IframeBridge.sendMessage('analytics_event', { event, ...payload })   // iframe: тип узгодити!
    else if (import.meta.dev) console.info('[analytics]', event, payload)          // standalone/dev
  }
  return { track }
}
```

Дублювання виключається самою архітектурою: один `track()` → рівно один канал.

## 5. UTM і кампанії

- В iframe UTM-мітки живуть на **батьківському** URL — лендінг їх не бачить і не парсить; атрибуція
  джерел — на боці продукту. Лендінг ідентифікує себе через `landing_id`.
- У standalone-режимі UTM працюють звичайно (GA сам їх підхоплює) — нічого не робити вручну.
- Не додавати UTM до лінків «усередину» продукту (`product`/`event_action`-дії) без запиту аналітиків —
  це може перебити атрибуцію сесії продукту.

## 6. Consent і приватність

- Події відлітають лише коли consent-контекст продукту це дозволяє: у full-page це гарантує сам
  продуктовий GA (лендінг пушить у dataLayer, а рішення про відправлення приймає контейнер);
  в iframe — батько вирішує, що робити з пересланими подіями. Лендінг не реалізує власний consent-банер.
- Жодних PII у параметрах (див. §2); `has_auth` — максимум персоналізації.

## 7. Хендоф продуктовим аналітикам (deliverable)

Передати аналітикам ОДИН документ (копія цього файлу із заповненими таблицями) з:

1. **Таблиця подій** (§3) з реальними `section_id`/`cta_id` кампанії — `cta_id` беруться напряму з
   `config/actions.ts`, тож список точний за побудовою.
2. **Спільні параметри** (§2) зі значеннями для цієї кампанії (`landing_id`, версія).
3. **Канал** (§4): узгоджений механізм (dataLayer / message-тип) + хто мапить події в GA4-property
   (custom definitions для нових параметрів створюють аналітики — параметри без реєстрації в GA4
   не з'являться у звітах).
4. **Приклад payload** кожної події (JSON) для перевірки в GA4 DebugView.
5. **Що лендінг НЕ шле** (page_view, PII, token) — щоб не шукали зайвого.

Чекліст перед релізом:

- [ ] Словник подій узгоджено з аналітиками; custom definitions створені в GA4.
- [ ] Канал для iframe-режиму підтверджено командою продукту (тип повідомлення існує на їхньому боці).
- [ ] `cta_id` у специфікації == `analyticsId` у `config/actions.ts` (автозвірка grep-ом).
- [ ] Події перевірені в GA4 DebugView на staging (усі відлітають один раз, з усіма параметрами).
- [ ] `scroll_depth`/`section_view` не спамлять (кожен поріг/секція — один раз на перегляд).
- [ ] PII-аудит параметрів: нічого особистого, token відсутній.
