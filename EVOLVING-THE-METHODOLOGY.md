# Як розвивати методологію

Ця методологія — **жива**. Вона стає точнішою з кожним новим лендінгом: рекомендації, перевірені на
практиці, стають спостереженнями; повторювані патерни підвищуються до правил; провали фіксуються, щоб не
повторюватись. Цей документ описує процес.

> Термінологія міток: **Спостережено** / **Виведено** / **Рекомендовано** (див. `README.md`).

## 1. Під час збірки лендінгу

- Використовуй методологію як вхід, а не як тягар: `LANDING-PROMPT-TEMPLATE.md` на старті, `PHASE-PROMPTS.md`
  пофазно, `CHECKLISTS.md` на гейтах.
- Веди `DECISION-LOG` цього лендінгу (копію шаблону — в репозиторії лендінгу, не тут): кожне нетривіальне
  рішення з причиною й наслідком.
- Позначай на льоту, що з методології **спрацювало**, що **довелось обійти**, а чого **бракувало**. Це
  сирі дані для ретроспективи.

## 2. Після лендінгу — ретроспектива

- Заповни `RETROSPECTIVE-TEMPLATE.md`. Її фінальна секція — «що оновити в методології» — і є списком
  конкретних змін-кандидатів.
- Правило підвищення міток:
  - Рекомендація, **перевірена на реальному лендінгу** → переклей мітку `Рекомендовано` → `Спостережено`
    (напр., коли iframe-контракт нарешті відпрацьовано — переведи весь iframe-розділ у `Спостережено` і
    підніми версію MINOR).
  - Патерн, що **повторився на 2+ лендінгах** → підвищ його статус і винеси в `STARTER-ARCHITECTURE.md`,
    якщо він придатний до перевикористання.
  - Новий інструмент/скіл, що дав користь → онови `CLAUDE-CODE-SKILLS.md`.
  - Помилка, що коштувала часу → додай у «типові помилки» відповідної фази у `LANDING-WORKFLOW.md` і в
    ретроспективний розділ головного документа.

## 3. Внесення змін (PR-процес)

```
git switch -c update/<короткий-опис>     # напр. update/iframe-verified
# редагуєш .md
git commit -m "docs: <що і чому>"
git push -u origin update/<короткий-опис>
gh pr create --fill                      # PR у цей репозиторій
```

Правила якості для будь-якого PR (той самий бар, що й для першої версії):

- [ ] Brand-neutral: жодних назв продукту/кампанії/маскота, жодних реальних hex-кольорів, жодної
      предметної специфіки. Приклади — generic.
- [ ] Кожне нове твердження має мітку `Спостережено`/`Виведено`/`Рекомендовано`.
- [ ] Узгодженість між файлами: назви фаз збігаються у `LANDING-WORKFLOW.md` і `PHASE-PROMPTS.md`; TOC
      головного документа == його заголовки; крос-рефи ведуть на реальні файли/секції.
- [ ] Оновлено `CHANGELOG.md` і, за потреби, версію.

## 4. Версіонування

Semver-подібно:

- **MAJOR** (`2.0.0`) — несумісна зміна процесу чи структури файлів (переставлені фази, перейменовані
  документи), яка ламає посилання наявних лендінгів на методологію.
- **MINOR** (`1.1.0`) — новий розділ, патерн, скіл або підвищення мітки (`Рекомендовано` → `Спостережено`).
- **PATCH** (`1.0.1`) — уточнення, правки, приклади, виправлення неузгодженостей.

Після merge познач тег:

```
git tag -a v1.1.0 -m "iframe contract verified on <project>"
git push origin v1.1.0
```

## 5. Використання в наступних лендінгах

Рекомендований спосіб — **git submodule**, запінений на тег версії, щоб лендінг залежав від
конкретної, відтворюваної версії методології:

```
# у репозиторії нового лендінгу:
git submodule add <git-url-методології> methodology
cd methodology && git checkout v1.0.0 && cd ..
git add . && git commit -m "chore: pin methodology v1.0.0"
```

Оновити методологію в лендінгу (свідомо, коли готовий):

```
cd methodology && git fetch --tags && git checkout v1.1.0 && cd ..
git commit -am "chore: bump methodology to v1.1.0"
```

Альтернатива без submodule — разова копія (`degit`/завантаження) у `docs/methodology/` лендінгу; тоді
покращення повертаєш вручну через PR у цей репозиторій.

