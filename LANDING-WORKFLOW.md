# Workflow лендінгу — від нульової ідеї до production і далі

> **Framework 2.0 notice:** цей 17-фазовий runbook лишається детальною технічною бібліотекою.
> Канонічні product/design/release гейти тепер визначені у [framework/README.md](framework/README.md).
> Не починай Скафолдинг/Реалізацію, доки не пройдено G7 Design Approved і G8 Asset Freeze.

До цієї технічної фази завжди виконуються: agent bootstrap → CATBET/SlotCity route → Product Truth →
PlayCity copy review → Brand Archive snapshot/Brand Bridge → storyboard → 3 image-based directions →
Hero approval → full 1440/440/430/375 approval → Asset Freeze. Фазу можна позначити `N/A`, але не
переставити або обійти без owner/rationale у PROJECT-STATE.

> Призначення: практичний, пофазовий runbook для побудови високоякісного інтерактивного промо-лендінгу (Nuxt 3 / Vue 3 / TypeScript, SSG-вивід, з можливістю embed у продуктову сторінку) — від чистого брифу через деплой до post-launch review.

## Як читати цей документ

Кожна фаза нижче — це станція на складальному конвеєрі. Для кожної фази ти отримуєш: **Input**, **Ключові дії**, **Skills** (лише реальні скіли Claude Code, задіяні або застосовні за каноном), **Артефакти на виході**, **Критерії готовності** (гейт, який треба пройти, щоб рухатися далі), **Типові помилки** та **Перевірки перед переходом далі**.

Твердження марковані:
- **Спостережено** — бачено безпосередньо в роботі референсної сесії або в її фінальному коді/білді.
- **Виведено** — обґрунтований висновок із того, що спостерігали.
- **Рекомендовано** — на перспективу; не обов'язково задіяне в референсній сесії.

Cross-references: `PHASE-PROMPTS.md` (готові до вставки промпти по фазах), `STARTER-ARCHITECTURE.md` (структура, токени, motion-патерни), `LANDING-DEVELOPMENT-METHODOLOGY.md` §12 (Performance) (бюджети та виграші), `LANDING-DEVELOPMENT-METHODOLOGY.md` §11 (Iframe Integration) (контракт full-page vs iframe). Назви фаз тут точно збігаються з `PHASE-PROMPTS.md`.

## Основний цикл: design → agree → build, перевіряй локально, деплой лише після апруву

**Спостережено.** Референсний білд йшов як багато дрібних ітеративних запитів, нашарованих поверх робочого ядра сторінки. Дві поведінки трималися наскрізь і мають вважатися сталими правилами:

1. **Design → agree → build.** Запропонуй напрям чи зміну, отримай явну згоду, тоді реалізуй. Не розширюй scope мовчки. Правки групувалися навколо двох осей: *scope зміни* (один блок vs. усюди) та *специфічна для mobile поведінка*. Виноси обидва питання наперед у кожному запиті — «які саме елемент(и)?» та «яким є mobile-трактування?»
2. **Спершу перевіряй на localhost; не деплой, доки не апрувнуто.** Користувач неодноразово просив локальну перевірку перед будь-яким деплоєм. Вважай локальну перевірку + явний апрув деплою жорстким гейтом, який жодна фаза не пропускає.

```
      ┌─────────────────────────────────────────────┐
      │  propose (design)  →  confirm (agree)        │
      │        ↓                                      │
      │  implement (build)  →  verify on localhost    │
      │        ↓                                      │
      │  approved?  ── no ──→ iterate ────────────────┘
      │        │ yes
      │        ↓
      │     deploy
```

Цей цикл вкладений *усередину* кожної фази нижче — гейти фаз є контрольними точками в тому ж ритмі, а не заміною йому.

## Фаза 1 — Discovery (дослідження)

**Input:** сирий бриф, ціль кампанії, будь-які наявні бренд/дизайн-референси, продуктовий контекст (де житиме лендінг).

**Ключові дії:**
- Обери destination product: CATBET або SlotCity; завантаж лише відповідний Product KB/Brand Archive.
- Класифікуй advertiser, host, destination, relationship, placement і 21+ treatment; активуй
  `playcity-copy-review`.
- Зафіксуй єдину конверсійну ціль (один головний CTA). Усе інше — вторинне.
- Визнач аудиторію, тон, будь-які legal/compliance-обмеження (age gating, обов'язкові legal-лінки, ліцензійні застереження).
- Визнач *ціль embed*: лендінг — це **full-page embed** (продукт постачає header/footer, лендінг заповнює простір між ними — **Спостережено** в референсній сесії) чи **iframe embed** (**Рекомендовано** для майбутніх лендінгів)? Це єдине рішення формує скафолдинг, CTA та стилізацію стиків.
- Інвентаризуй наявні асети та можливості генерації асетів (image/video-генерація через MCP, CDN-хостинг).

**Skills:** project-local `promo-landing-framework`; `playcity-copy-review`; source/browser inspection.

**Артефакти на виході:** коротка нотатка продуктової правди (ціль, аудиторія, один CTA, джерело реального копірайту, compliance-список), рішення щодо режиму embed (або позначка, що воно ще відкрите).

**Критерії готовності (гейт):** одну конверсійну ціль записано; аудиторію і тон узгоджено; режим embed обрано або явно відкладено з призначеним owner; compliance-обмеження перелічено.

**Типові помилки:**
- Вигадування метрик, testimonials або цифр, яких немає в брифі (**Спостережено** анти-патерн, якого варто уникати).
- Копіювання конкретного референсного сайту замість витягування принципів.
- Залишити режим embed невирішеним після скафолдингу — переробляти це дорого.

**Перевірки перед переходом далі:** Чи можеш ти сформулювати єдину задачу сторінки одним реченням? Чи знаєш ти, де її буде embed і хто постачає chrome?

## Фаза 2 — Нормалізація вимог

**Input:** нотатка з Discovery.

**Ключові дії:**
- Переклади розмиті прохання в нормалізований список вимог: performance-бюджети, планка accessibility, breakpoints для підтримки, очікування щодо reduced-motion, browser matrix.
- Явно запінь стек, щоб уникнути framework drift: **Nuxt 3 (не 4)**, Vue 3, TypeScript, `<script setup lang="ts">`, SSG через `nuxi generate`, вручну написані CSS-токени (без Tailwind/UI kit), GSAP + ScrollTrigger для motion, npm + закомічений lockfile (**Спостережено** стек).
- Запиши відомі обмеження середовища наперед — напр. **Спостережено:** немає локальних `ffmpeg`/`cwebp`/`avifenc`/`pyftsubset`, тож транскодинг медіа має відбуватися на етапі генерації або через опції build-модуля, а не на диску.
- Визнач performance-бюджети як цілі (напр. JS ≤ ~180KB gzip; LCP — це poster-зображення; див. `LANDING-DEVELOPMENT-METHODOLOGY.md` §12 (Performance)).

**Skills:** `best-practices`, `web-design-guidelines` (як референс планки, ще не як гейт).

**Артефакти на виході:** таблиця вимог (бюджети, планка a11y, breakpoints, browser matrix, політика reduced-motion), заява про запінений стек, нотатка про обмеження середовища.

**Критерії готовності (гейт):** стек запінено письмово; бюджети та політику a11y/reduced-motion узгоджено; обмеження середовища відомі.

**Типові помилки:**
- Дати скілу чи прикладу підштовхнути проєкт до layout **Nuxt 4** (`app/` srcDir, нові aliases) чи патернів React/Next (**Спостережено** застереження — скіл `nuxt` написано під Nuxt 4, і його Nuxt-4-специфіку тут треба ігнорувати; `design-taste-frontend` постачає React-приклади, які треба транслювати у Vue).
- Сприймати розміри bundle у dev-режимі як реальні — справжні цифри дають лише production-білди.

**Перевірки перед переходом далі:** Чи стек однозначний? Чи бюджети числові й тестовані?

## Фаза 3 — Концепція

**Input:** нормалізовані вимоги.

**Ключові дії:**
- Згенеруй рівно 3 **image-based** direction-кандидати з exact brand sources (layout, type pairing,
  palette intent, interaction vocabulary, anti-patterns). Prose-only direction не проходить.
- Звузь до **однієї** сильної art-direction-концепції: одна central visual metaphor, один контрольований aesthetic risk. Відхиляй формулу-шаблон (centered hero + gradient + три однакові картки + glassmorphism).
- Свідомо вибудуй послідовність дизайн-пайплайну: product truth → design intelligence → art direction. Не змішуй усі дизайнерські інструкції одночасно (**Спостережено** дисципліна).

**Skills:** Product Design `ideate`, тоді один `creative-director` review. Exact names можуть
відрізнятися; capability contract — у [SKILLS-MANIFEST.md](SKILLS-MANIFEST.md).

**Артефакти на виході:** concept brief — обрана метафора, palette intent, type pairing, одна signature-інтеракція та явний список анти-патернів.

**Критерії готовності (гейт):** одну концепцію обрано й узгоджено (design → agree); названо central metaphor і один свідомий ризик; анти-патерни записано.

**Типові помилки:**
- Запуск першої ідеї без альтернатив.
- Плутати «більше ефектів» з art direction.
- Пропуск кроку «agree» і побудова концепції, яку stakeholder ніколи не апрувнув.

**Перевірки перед переходом далі:** Чи можеш ти назвати метафору та один ризик — по реченню на кожне? Чи задумана mobile art direction як окрема річ, а не зменшений desktop (**Спостережено** правило проєкту)?

## Фаза 4 — Розкадровка (storyboard)

**Input:** concept brief.

**Ключові дії:**
- Розклади послідовність секцій за системою прийняття рішень щодо ролі секції (не за фіксованим шаблоном): **Hero → Value/Explanation → Mechanics/Benefits → Visual storytelling → Proof/Trust → FAQ/Legal → Final CTA**. Обери ролі, яких ця кампанія справді потребує.
- Для кожної секції: визнач її задачу, форму копірайту (headline/body/list), задуманий motion beat і трактування desktop-vs-mobile.
- Познач, яка секція несе «signature»-інтеракцію, а які тихі.

**Skills:** `frontend-design`, `creative-director` для наративного потоку.

**Артефакти на виході:** storyboard (впорядковані секції з роллю, формою копірайту, motion beat та mobile-нотаткою на кожну секцію).

**Критерії готовності (гейт):** кожна секція має роль, призначення та mobile-трактування; розміщення CTA свідоме; storyboard узгоджено.

**Типові помилки:**
- Одна секція тихо виростає в монстра пізніше — вирішуй наперед, яка секція є важкою «visual storytelling», і що її motion-модель має бути замінюваною (**Спостережено:** пізній запит «перебудуй інтеракцію цієї секції» натякає, що motion-модель варто було вирішити й зробити замінюваною раніше; одна секція дійшла до ~692 рядків).
- Не записано mobile-трактування для кожної секції, що змушує імпровізувати пізніше.

**Перевірки перед переходом далі:** Чи послідовність розповідає історію, що завершується на CTA? Чи ідентифіковано важку секцію?

## Фаза 5 — Технічний план

**Input:** storyboard + запінений стек.

**Ключові дії:**
- Виріши структуру компонентів. **Спостережено** структура, що спрацювала: тонка оболонка `app.vue` (root class + `<main>`, що перелічує компоненти секцій), один компонент на секцію, який володіє власним animation lifecycle, перевикористовувані декоративні primitive з prop `uid`, щоб уникнути колізій SVG id.
- **Рекомендовано** для перевикористовуваного starter: розділи `components/` (загальні primitive) від `sections/` (секції сторінки); додай `motion/` (animation composables + токени), `config/` + `content/` (data-driven копірайт/асети), `utils/`, `types/`.
- Сплануй шар токенів (`assets/css/tokens.css`) і базовий шар (`assets/css/base.css`: reset, primitive, reduced-motion, ambient keyframes).
- Сплануй client-only плагіни: реєстрація GSAP/ScrollTrigger, Lenis smooth scroll (через `gsap.ticker`), спільний IntersectionObserver, що ставить на паузу offscreen ambient-анімації.
- Виріши контракт embed зараз (full-page vs iframe) — див. `LANDING-DEVELOPMENT-METHODOLOGY.md` §11 (Iframe Integration).
- Виріши content-модель: inline-в-компоненті (швидко, **Спостережено**) vs. content-config шар (дешевші свопи теми/копірайту, **Рекомендовано**).

**Skills:** `nuxt`, `vue` (ігноруй їхню Nuxt-4 / React-специфіку за каноном).

**Артефакти на виході:** рішення щодо директорій/структури, список категорій токенів, список плагінів, контракт embed, рішення щодо content-моделі.

**Критерії готовності (гейт):** структуру й план токенів записано; плагіни перелічено; контракт embed обрано; content-модель обрано.

**Типові помилки:**
- Відкладання рішення щодо content-моделі, а потім хардкодинг копірайту всередині кожного компонента (**Спостережено** запах rework — нормально для одного лендінга, дорого перетемувати).
- Не спланована z-index-шкала — веде до багів стекінгу (**Спостережено**: фіксоване поле фонового декору на `z-index:-1`, per-section декор `z-index:0`, контент `z-index:1+`, grain над фоном).

**Перевірки перед переходом далі:** Чи міг би другий інженер заскафолдити з цього плану самого по собі? Чи задокументовано z-index-нашарування?

## Фаза 6 — Дизайн-основи

**Input:** технічний план.

**Ключові дії:**
- Напиши `tokens.css`: колір (bg/surface, один primary accent, secondary, alert), типографіка (`--font-display`, `--font-ui`, fluid `clamp()`-шкала, ваги), spacing-шкала, `--radius-pill` + висоти кнопок, section padding, motion-тривалості (`--t-micro`, `--t-ui`) + easing (`--ease-enter`), z-index-шкала (`--z-decor`, `--z-content`), ширина `--container`.
- **Рекомендовано** додатки для перевикористання: токени shadow, blur, opacity, breakpoints, інтенсивності декоративних ефектів — щоб новий лендінг перестилізовувався редагуванням токенів, а не компонентів.
- Напиши `base.css`: reset, primitive кнопок/заголовків, primitive reveal-on-scroll, правила reduced-motion, ambient `@keyframes`.
- Налаштуй шрифти через font-модуль (Google provider, self-hosted на білді): один display-накреслення + один UI/text-накреслення. Заплануй **subsetting** (найбільший performance-важіль — див. Фазу 12 та `LANDING-DEVELOPMENT-METHODOLOGY.md` §12 (Performance)).

**Skills:** `impeccable` (проходи `typeset`/`colorize`), `ui-ux-pro-max`, `frontend-design`.

**Артефакти на виході:** `assets/css/tokens.css`, `assets/css/base.css`, конфігурація шрифтів.

**Критерії готовності (гейт):** токени споживаються всюди через `var(--x)` (жодних сирих hex/px, розкиданих по компонентах); primitive reduced-motion існують; шрифти налаштовано з планом subsetting.

**Типові помилки:**
- Глобальні reset, що воюють зі свідомими винятками (**Спостережено**: `img{max-width:100%}` обрізав навмисно збільшене зображення → знадобився escape hatch `max-width:none`). Документуй escape hatches.
- Застосування зміни токена до УСІХ елементів, коли мав змінитися лише один блок (**Спостережено** over-reach → відкочено). Обмежуй візуальні зміни точно названим елементом.

**Перевірки перед переходом далі:** Чи можеш ти перестилізувати палітру, редагуючи лише `tokens.css`? Чи є стратегія гейтингу через `html.js`, щоб без JS показувався весь контент?

## Фаза 7 — Скафолдинг проєкту

**Input:** дизайн-основи + рішення щодо структури.

**Ключові дії:**
- Заскафолди Nuxt 3, пінячи `nuxt@^3`; npm install; закомить lockfile.
- Налаштуй `nuxt.config.ts` під SSG: конфіг font-модуля (включно з subsetting `glyphs`/`text`), `app.head` (LCP preload, meta) та `experimental.payloadExtraction: false` для єдиного бездатного статичного роуту (прибирає зайвий запит `_payload.json` — **Спостережено** виграш).
- Створи оболонку `app.vue`, заглушки компонентів секцій, декоративні primitive, composables (`useMotionPrefs`, magnetic-hover helper) та client-плагіни (GSAP, Lenis, idle-sections observer).
- Підключи root scoping-клас, щоб усі стилі лендінга були scoped (критично для full-page embed — жодних глобальних reset, що протікають у продуктовий chrome).

**Skills:** `nuxt`, `vue`.

**Артефакти на виході:** запущений dev-скафолд з порожніми секціями, що рендеряться, застосованими токенами, зареєстрованими плагінами.

**Критерії готовності (гейт):** `npm run dev` рендерить оболонку без console-помилок; production `nuxi generate` успішний; стилі scoped під root-класом.

**Типові помилки:**
- Browser globals (`window`, `document`, observers) використані поза `onMounted`/client-плагінами/`import.meta.client` → поломка SSR.
- Lock dev-сервера, що блокує `generate` (**Спостережено**: використовуй `NUXT_IGNORE_LOCK=1`); `zsh`-квірки на кшталт `declare -A` «bad substitution».

**Перевірки перед переходом далі:** Чи `nuxi generate` завершується чисто? Чи всі browser-only API client-gated?

## Фаза 8 — Реалізація Hero

**Input:** скафолд + hero-специфікація зі storyboard.

**Ключові дії:**
- Побудуй hero з **LCP як responsive poster `<img>`**, preloaded через `imagesrcset`/`imagesizes` + `fetchpriority="high"` — ніколи не відео.
- Якщо hero-відео існує, воно грає *поверх* poster і ніколи не має ставати LCP. Дай йому `preload="none"` та play, керований IntersectionObserver; надай статичний poster під reduced-motion.
- Дай кожному media-елементу явні width/height або aspect-ratio (контроль CLS).
- Реалізуй hero CTA як реальне посилання на продуктовий роут (без placeholder). Для iframe embed CTA, які мають навігувати top window, потребують `target="_top"` або postMessage-мосту (**Рекомендовано** — див. `LANDING-DEVELOPMENT-METHODOLOGY.md` §11 (Iframe Integration)).

**Skills:** `frontend-design`, `core-web-vitals`, `performance`.

**Артефакти на виході:** повна hero-секція з poster LCP, опційним gated-відео, реальним CTA.

**Критерії готовності (гейт):** hero рендериться; LCP — це poster-зображення, preloaded; немає подвійного fetch poster (**Спостережено**: надлишковий `<video poster=...>` спричиняв подвійний fetch — прибери його); CTA вказує на реальний роут.

**Типові помилки:**
- Виклик `.play()` на mount, що змушує до жадібного завантаження відео (**Спостережено**: відео нижче лінії згину жадібно завантажило ~3.4MB — хай IntersectionObserver буде єдиним драйвером play).
- Placeholder CTA hrefs, відвантажені випадково.

**Перевірки перед переходом далі:** Чи в network-панелі poster є LCP, а відео не завантажується, доки не стане видимим? Нульовий CLS на завантаженні hero?

## Фаза 10 — Motion

**Input:** усі секції відрендерені (статичні).

**Ключові дії:**
- Обгорни GSAP у `gsap.context(scope)`; чисти через `ctx.revert()` + `ScrollTrigger.kill()` у `onUnmounted`. Реєструй плагіни лише на клієнті.
- Гейти scroll-анімації через `gsap.matchMedia('(prefers-reduced-motion: no-preference)')`; reduced-шлях виставляє фінальні стани миттєво.
- Reveal-on-scroll: анімуй лише opacity/transform (compositor-friendly).
- Для будь-якої кастомної `requestAnimationFrame`-сцени: лише transform на кадр, `will-change:transform` лише на рухомих елементах, пауза offscreen через IntersectionObserver **з time-continuity** (акумулюй паузований час, щоб motion відновлювався безшовно), пере-вимірювання через ResizeObserver, гейти cursor-parallax до `(hover:hover) and (pointer:fine)` та надавай статичний layout під reduced-motion.
- Інтегруй Lenis через `gsap.ticker.add(t => lenis.raf(t*1000))`; повністю пропускай під reduced-motion.
- Ambient `@keyframes` (drift/spin/float) є compositor-only і паузуються offscreen спільним IntersectionObserver-плагіном.

**Skills:** `impeccable` (прохід `animate`), `performance`.

**Артефакти на виході:** повний motion-шар з reduced-motion-паритетом та offscreen-паузуванням.

**Критерії готовності (гейт):** reduced-motion повністю дотримано (без scrub/parallax/pinning/autoplay; статичні poster); немає нескінченної offscreen ambient-анімації; cleanup перевірено наскрізь навігацію (без дубльованих listeners/timelines).

**Типові помилки:**
- Створення GSAP tween **на кожному scroll-кадрі** в `onUpdate` (**Спостережено** баг — tween лише на перемиканні стану).
- rAF read/write thrash та per-frame алокації (**Спостережено** — гейти per-frame роботу; `getBoundingClientRect()` на кожен mousemove — це forced reflow, тож зваж design-ризик виправлення перед кешуванням).
- Reduced-motion статичний layout, що не перераховується на resize (**Спостережено** — винеси reduced-прапор нагору; пере-запускай на ResizeObserver).
- Для зациклених рухомих елементів: майже рівні періоди спричиняють колізії (**Спостережено**). Дай кожному рухомому елементу **однаковий кутовий період + рівномірно розкидані фази**; варіюй per-mover радіус для глибини; доведи відсутність колізій математичною симуляцією перш ніж довіряти оку; сховай стик циклу за межами екрана.

**Перевірки перед переходом далі:** Чи `prefers-reduced-motion` дає повністю статичну, одразу придатну до використання сторінку? Чи анімації паузуються, коли їхня секція offscreen? Чи доведено будь-який loop-інваріант симуляцією (див. `LANDING-DEVELOPMENT-METHODOLOGY.md` §16 (QA) / §17 (Definition of Done))?

## Фаза 11 — Адаптив

**Input:** desktop motion + layout завершено.

**Ключові дії:**
- Трактуй mobile як **окрему art direction**, а не зменшений desktop.
- Fluid-розміри через `clamp(min, vw, max)`; використовуй `svh`/`dvh` з fallbacks; шануй safe-area та coarse-pointer.
- Тестуй на 320/360/375/390/768/1024/1440 + landscape.
- Для будь-чого, затиснутого між двома краями (напр. текстовий блок, прив'язаний угорі, і арт, прив'язаний унизу), **виміряй реальний вільний зазор у runtime** (у `measure()` на mount + ResizeObserver) і прив'язуй motion до цього виміряного зазору — не використовуй математику fraction-of-viewport.

**Skills:** `web-design-guidelines`, `playwright-cli` (viewport-перевірки), `accessibility`.

**Артефакти на виході:** реалізовано mobile art direction; адаптивну поведінку перевірено по всій матриці ширин.

**Критерії готовності (гейт):** немає горизонтального overflow на жодній тестованій ширині (перевір `scrollWidth - clientWidth === 0`); mobile має власну art direction; touch targets та safe-area дотримано.

**Типові помилки:**
- Fraction-of-viewport геометрія motion, що штовхає анімаційну дугу в текст на коротких viewport (**Спостережено** rework → фікс через виміряну смугу). Виріши модель прив'язки (виміряна vs fractional) наперед.
- Припущення `100vh` — використовуй `100dvh` з fallback.

**Перевірки перед переходом далі:** Нульовий горизонтальний overflow усюди? Чи mobile-досвід відчувається спроектованим, а не стиснутим?

## Фаза 12 — Оптимізація асетів

**Input:** усе медіа на місці, з посиланням на локальні чи згенеровані асети.

**Ключові дії:**
- **Subset-нь шрифти** — найбільший одиничний виграш. CJK-здатний display-шрифт може inline'ити ~120 невикористаних unicode-range-зрізів у HTML. Subset-нь server-side через опцію `glyphs`/`text` font-модуля точно до тих гліфів, що рендеряться. **Надай повний алфавіт, що реально використовується**, щоб жоден гліф не впав у fallback. (**Спостережено**: `@font-face` 138→19, distinct woff2 122→3, `index.html` 54KB→14.6KB gzip.)
- Підтверди `font-display: swap` + metric-matched fallback (`size-adjust`/`ascent-override`) для near-zero swap CLS (font-модуль може їх інжектити).
- Підтверди, що LCP poster preloaded/eager/`fetchpriority=high`; усе інше `loading="lazy"` + `decoding="async"`; відео `preload="none"` + IO-gated.
- Хости бінарні асети на CDN. **Спостережено** розблокування: inline deploy-tools не можуть відвантажувати великі бінарники — завантажуй згенеровані асети на CDN (запит presigned URL → PUT → confirm → отримати permanent URL) і посилайся за URL. Стіли як WebP з responsive `srcset`/`sizes`; прозорий декор як PNG/WebP; poster-кадр на кожне відео.

**Skills:** `performance`, `core-web-vitals`, `seo`.

**Артефакти на виході:** subset-шрифти, оптимізоване/захостоване медіа, легкий `index.html`.

**Критерії готовності (гейт):** кількість `@font-face` схлопнута до реально використовуваних накреслень; `index.html` легкий; LCP poster preloaded; усі бінарники на CDN з реальними URL.

**Типові помилки:**
- Припущення, що шрифт нормальний без аудиту зібраного HTML — **виміряй, які зрізи реально inline'яться/завантажуються** (**Спостережено** урок).
- Очікування транскодити відео/зображення на диску, коли в середовищі бракує `ffmpeg`/`cwebp`/`avifenc`/`pyftsubset` (**Спостережено** обмеження — роби роботу з форматами на етапі генерації або через опції build-модуля).
- Пропущений гліф у subset → видимий fallback-символ.

**Перевірки перед переходом далі:** Чи gzip-розмір production `index.html` відповідає цілі? Чи кожен асет — це CDN URL, нуль локальних шляхів?

## Фаза 13 — Iframe/embed-інтеграція

**Input:** завершений лендінг + рішення щодо embed з Фази 1/5.

**Ключові дії:**

*Якщо full-page embed (Спостережений шлях):*
- Лендінг **не має власного header/footer**; продукт постачає їх. Не дублюй навігацію.
- Кольорово підбери верхній і нижній краї до темного chrome продукту для безшовного стику; підтверди висоту/stickiness header та background-кольори з продуктовою командою.
- Тримай усі стилі scoped під root-класом; жодних агресивних глобальних reset; не чіпай продуктові cookies/localStorage/глобальні стилі.
- CTA — це звичайні посилання на продуктові роути (візьми точні URL у команди); зовнішні лінки `rel="noopener noreferrer"`.
- Врахуй sticky header у ScrollTrigger-offsets; ніколи не перехоплюй scroll.

*Якщо iframe embed (Рекомендовано / Виведено — НЕ задіяно в референсній сесії):*
- Не припускай нічого про parent (width, тема, шрифти, CSP). Заповнюй 100% ширини; ніколи не фіксовану px-ширину.
- Child вимірює власну висоту (ResizeObserver на `document.documentElement`) і `postMessage`-ить її нагору; parent ресайзить iframe. Використовуй версіонований контракт `{ source:'landing', type, payload }` з origin allow-listing.
- CTA, які мають навігувати top window, використовують `target="_top"` або `postMessage({type:'navigate'})`, який parent шанує.
- Жодної залежності від third-party cookies; жодного auth у query strings; не чіпай parent storage.
- Надай `landingReady` handshake, loading-стан, integration-error fallback та standalone URL для тієї ж сторінки. **Рекомендований deliverable:** composable `useIframeBridge()` (child) + parent-сніпет (handshake, debounced height autosize, navigation-запити, форвардинг аналітики, усе origin-checked).

**Правило рішення:** обирай full-page embed, коли ти контролюєш продуктову оболонку і хочеш безшовний single-document досвід; обирай iframe, коли лендінг має вставлятися в поверхню, яку ти не контролюєш, потребує ізоляції або обслуговується з іншого origin.

**Skills:** `best-practices`, `web-design-guidelines`.

**Артефакти на виході:** робочий embed (seam-matched full-page або iframe-міст + parent-сніпет), плюс standalone URL.

**Критерії готовності (гейт):** стик embed чистий; немає забруднення глобального стану; CTA навігують коректно в обраному режимі; standalone URL існує.

**Типові помилки:**
- (Full-page) протікання глобальних reset у продуктовий chrome; дублювання header/footer.
- (Iframe) голе посилання всередині cross-origin iframe навігує iframe замість продукту; покладання на cross-origin `scrollHeight`-читання (неможливо — child має сам себе виміряти і повідомити нагору).

**Перевірки перед переходом далі:** Чи сидить лендінг усередині продуктового chrome (чи iframe) без візуальних стиків і console-помилок? Чи CTA досягають наміченого top-level роуту?

**Див.** `LANDING-DEVELOPMENT-METHODOLOGY.md` §11 (Iframe Integration) для повного контракту та ескізу `useIframeBridge()`.

## Фаза 15 — QA

**Input:** feature-complete лендінг.

**Ключові дії:**
- Збери **реальний production-білд** (`nuxi generate`) для справжніх розмірів JS/CSS/HTML/шрифтів — ніколи не довіряй числам dev-режиму.
- Використовуй browser MCP для: console-помилок, network (що реально завантажується), computed layout, above-the-fold скриншотів, responsive resize, DOM-assertions через `javascript_tool`.
- Доведи animation-інваріанти (відсутність колізій, зазор від тексту/арту, безшовний loop) **математичними симуляціями** в консолі *до того*, як довіряти оку — особливо там, де середовище не може скролити/спостерігати motion нижче лінії згину.
- Проведи **adversarial multi-agent review**: кожна знахідка незалежно верифікована на correctness, framework-validity, design-safety та net-win перед прийняттям; відхиляй знахідки, що провалюють будь-що (напр. micro-opt, що не є design-safe).

**Skills:** `web-quality-audit`, `playwright-cli`, `accessibility`, `performance`, `core-web-vitals`, `seo`, `best-practices`, `impeccable` (прохід `audit`). Вони мають право veto щодо accessibility/usability/security/performance, але виправляють execution, а не art direction.

**Артефакти на виході:** QA-звіт з верифікованими знахідками, застосованими виправленнями та зеленим production-білдом.

**Критерії готовності (гейт):** немає console-помилок на production-білді; бюджети дотримано; CLS під контролем; reduced-motion дотримано; немає горизонтального overflow на жодній ширині; усі CTA реальні; стик embed чистий. (Див. Definition-of-Done у `LANDING-DEVELOPMENT-METHODOLOGY.md` §16 (QA) / §17 (Definition of Done).)

**Типові помилки:**
- Довіра розмірам dev-режиму чи неозброєному оку щодо коректності motion.
- Застосування знахідки review без перевірки її blast radius чи design-safety (**Спостережено**: cache-«фікс» відхилено як не design-safe — виміряй ризик виправлення, а не лише знахідку).
- Обмеження browser-MCP, які треба планувати обійти (**Спостережено**): не можна скриншотити нижче лінії згину; smooth-scroll бібліотеки блокують програмний scroll; IO може не спрацьовувати на CSS-transform зсувах — покладайся на JS-вимірювання + матсими.

**Перевірки перед переходом далі:** Чи production-білд чистий і в межах бюджету? Чи кожна прийнята знахідка пройшла незалежну верифікацію?

## Фаза 16 — Деплой

**Input:** білд, що пройшов QA + явний апрув деплою (сталий гейт).

**Ключові дії:**
- Підтверди, що користувач апрувнув деплой — ніколи не деплой на припущенні (**Спостережено** сталe правилo).
- Трансформуй локальні шляхи `/img`/`/video` → CDN URL через build-скрипт, окремо обробляючи компоненти, що будують шляхи динамічно (`prefix + name`, `${var}`-шаблони), у явні URL-поля.
- **Валідуй перед деплоєм:** запиши трансформовані файли в temp-директорію з symlink `node_modules` і запусти `nuxi generate`; засерти **0 локальних asset-шляхів** та очікувану кількість `@font-face`.
- Деплой source → host білдить (напр. Vercel `deploy_to_vercel`, production; **опусти teamId** — його передача спричинила 403). Делегуй емісію великого payload субагенту заради context hygiene.
- Верифікуй live: curl/завантаж production URL і засерти маркери (title, CTA-текст, CDN asset-refs, немає error-сторінки, немає console-помилок).

**Skills:** нічого специфічного; deploy MCP + `web-quality-audit` для live-перевірки.

**Артефакти на виході:** live production URL, лог валідації (0 локальних шляхів, коректна кількість шрифтів), нотатка post-deploy верифікації.

**Критерії готовності (гейт):** live URL віддає сторінку з коректними title/CTA/CDN-асетами, немає error-сторінки, немає console-помилок; валідація засертила 0 локальних asset-шляхів перед деплоєм.

**Типові помилки:**
- Передача явного `teamId` → 403 (**Спостережено** — опусти його).
- Base64-inlining бінарників через tool call (непрактично — **Спостережено** — хости на CDN, посилайся за URL).
- Деплой без pre-deploy build-валідації.

**Перевірки перед переходом далі:** Чи live-сторінка проходить marker-assertions? Чи pre-deploy валідація підтвердила нуль локальних шляхів?

## Фаза 17 — Post-launch review (ретроспектива)

**Input:** live-лендінг + будь-які field-дані.

**Ключові дії:**
- Захопи field Core Web Vitals (LCP/INP/CLS at p75), щойно з'явиться трафік; порівняй із бюджетами. (**Спостережено** прогалина: немає in-loop Lighthouse/field-CWV runner — **Рекомендовано** додати такий.)
- Ретроспектива щодо rework: виноси наперед рішення, що спричинили ітерацію — scope кожної зміни (один елемент vs усюди), mobile-трактування на запит та motion-модель важкої секції (зроби її замінюваною раніше).
- Зазнач, що ця референсна сесія використала **full-page embed**, тож уся **iframe**-настанова лишилася перспективним контрактом (Рекомендовано/Виведено), не задіяним — познач це для наступного проєкту, який справді потребує iframe.
- Запиши обмеження середовища на наступний раз (немає локального media-toolchain; scroll/IO-обмеження browser-MCP).
- Поверни learnings назад у `config`/`content`-нашарування та додатки токенів, щоб наступний лендінг перетемувався редагуванням токенів/config, а не компонентів.

**Skills:** `web-quality-audit`, `core-web-vitals`, `performance`.

**Артефакти на виході:** нотатка ретроспективи, field-CWV снапшот (коли доступний), backlog покращень перевикористовуваного kit.

**Критерії готовності (гейт):** field-метрики захоплено або є план їх захопити; ретроспективу написано; backlog перевикористовуваного kit оновлено.

**Типові помилки:**
- Пропуск ретроспективи та повторення тих самих промахів front-loading наступного разу.
- Подання неперевіреної iframe-настанови як доведеної — тримай її маркованою Рекомендовано/Виведено.

**Перевірки перед переходом далі:** Чи уроки записані там, де наступний білд їх знайде? Чи реальність iframe-vs-full-page чесно зафіксована?
