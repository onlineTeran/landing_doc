# Шаблон ретроспективи лендінгу

> Призначення: універсальний post-launch review за принципом «заповни пропуски» для високоякісного інтерактивного промо-лендінгу (Nuxt 3 / Vue 3 / TS, SSG, embeddable), що використовується для фіксації уроків і повернення їх у методологію.

## Як користуватися цим документом

1. Скопіюй цей файл у репозиторій лендінгу (наприклад, `docs/retro-<landing-slug>.md`) на фазі **Post-launch review** (див. термінологію у списку фаз методології).
2. Заповни кожну секцію нижче. Тримай записи стислими — один рядок на пункт.
3. Позначай будь-яке неочевидне твердження як **Спостережено** (побачено в цьому build/logs), **Виведено** (виснувано міркуванням) або **Рекомендовано** (запропоновано на наступний раз).
4. Фінальна секція — *Що оновити в методології* — це payload. Кожен повторюваний урок переходить з ретро окремого лендінгу у спільні доки (див. cross-references внизу).

Спершу заповни хедер:

| Поле | Значення |
|---|---|
| Лендінг / кампанія (внутрішній slug) | `<slug>` |
| Використаний режим вбудовування | full-page embed / iframe embed |
| Рендеринг | SSG (`nuxi generate`) / інше |
| Запінена версія стеку | Nuxt `<x.y>` / Vue `<x.y>` / TS |
| Ціль деплою | `<host>` + `<CDN>` |
| Дата збірки / рецензент | `<date>` / `<name>` |

## 1. Що вдалося добре

Перелічи практики, які варто повторити дослівно. Для кожної зазнач *чому* вона спрацювала, щоб вона лишилася правилом, а не випадковістю.

- `<practice>` — `<why it worked>` — *Спостережено/Виведено*
- …

<details><summary>Загальний заповнений приклад (лише для ілюстрації)</summary>

- Тонкий app shell + один компонент на секцію, кожен володіє власним animation lifecycle (`gsap.context` + cleanup) — жодної animation-логіки на рівні template, тож секції лишалися незалежно редагованими. *Спостережено*
- Декоративні primitive-и брали prop `uid`, щоб namespace-ити id інлайнових SVG — переви­користані по секціях без жодних колізій id. *Спостережено*
- «Перевіряй на localhost, деплой лише після явного апруву» трактувалося як постійний гейт — ловило проблеми до того, як вони потрапляли в продакшн. *Спостережено*

</details>

## 2. Де втрачався час

Переробки, глухі кути й churn, якого можна було уникнути. Назви *рішення, яке мало відбутися раніше*.

| Симптом | Корінна причина | Правило «вирішити раніше» на наступний раз |
|---|---|---|
| `<what went wrong>` | `<why>` | `<the rule>` |

<details><summary>Загальний заповнений приклад (лише для ілюстрації)</summary>

| Симптом | Корінна причина | Правило «вирішити раніше» |
|---|---|---|
| Style-токен змінили в *усіх* заголовках, хоча йшлося лише про один блок. | Blast radius глобального редагування не був підтверджений. | Обмежуй кожну візуальну зміну до точно названого елемента; підтверджуй blast radius перед глобальним редагуванням токена. |
| Interaction-модель секції перебудовували пізно в проєкті. | Motion-модель для тієї секції не була вирішена/зроблена swappable наперед. | Вирішуй (та ізолюй) motion-модель кожної секції на фазі Технічного плану. |
| Mobile motion arc стикався з текстом на коротких viewport-ах. | Геометрію прив'язали до часток viewport замість виміряної вільної зони. | Коли два елементи прив'язані до різних країв, виводь вільну зону через runtime-вимірювання, а не частки viewport. |

</details>

## 3. Які prompt-и / інструкції спрацювали

Зафіксуй формулювання та послідовність, що дали хороший вивід — вони стають переви­користовними фрагментами prompt-ів.

- `<prompt pattern>` → `<result>` — *Спостережено*
- …

<details><summary>Загальний заповнений приклад (лише для ілюстрації)</summary>

- Запуск дизайн-пайплайну **послідовно** (product truth → design intelligence → art direction → implementation → craft passes → reality check), а не все одночасно, тримав кожен прохід сфокусованим. *Спостережено*
- Питання «Які саме елемент(и) і яка mobile-обробка?», задане *на кожен change request*, скоротило цикли виправлень. *Спостережено*
- **Adversarial multi-agent audit** («кожна знахідка незалежно верифікується на correctness, framework-validity, design-safety і net-win перед прийняттям») виявив реальні виграші й коректно відхилив небезпечні мікрооптимізації. *Спостережено*

</details>

## 4. Де помилявся AI

Помилки, яких припустився асистент — over-reach, хибні припущення, плутанина з framework, небезпечні фікси. Будь прямим; саме звідси беруться guardrail-и.

| Помилка | Як її зловили | Guardrail, який додати |
|---|---|---|
| `<error>` | `<detection>` | `<guardrail>` |

<details><summary>Загальний заповнений приклад (лише для ілюстрації)</summary>

| Помилка | Як її зловили | Guardrail |
|---|---|---|
| Глобальний `img { max-width:100% }` обрізав навмисно збільшене зображення. | Візуальний review. | Глобальні reset-и потребують задокументованих escape hatch-ів (`max-width:none` на позначених винятках). |
| Незахищений tween створювався щокадру всередині scroll-callback. | Perf review. | Захищай per-frame роботу; tween-ь лише на зміні стану. |
| Слідування Nuxt-4-конвенціям скіла (`app/` srcDir, нові aliases) у Nuxt-3-проєкті. | Тертя на build/lint. | Пінь версію framework як source of truth; явно ігноруй off-version поради скіла. |

</details>

## 9. Ретроспектива режиму вбудовування

Зазнач, який режим використовувався і чи витримав шов. Якщо специфіка iframe **не** була задіяна (наприклад, використовувався full-page embed), скажи про це явно — не подавай неперевірену поведінку iframe як верифіковану.

- Використаний режим: `<full-page embed / iframe embed>` — *Спостережено*
- Якість шва (кольори країв збігаються з product chrome; без подвійного header/footer; CTA потрапляють у реальні роути): `<notes>`
- Якщо iframe: height autosize, навігація `target="_top"`, origin allow-listing, handshake — `<tested? / N/A this build>`

<details><summary>Загальний заповнений приклад (лише для ілюстрації)</summary>

- Використано **full-page embed**: продукт надав header/footer, лендінг заповнив середину, стилі scoped під одним root-класом, кольори країв збіглися з темним chrome продукту. Шов був чистий. **iframe bridge тому НЕ був задіяний** — його контракт height-autosize / `target="_top"` / origin-check лишається *Рекомендовано*, не верифікованим. *Спостережено*

</details>

### Нагадування про чесність міток

Ніколи не записуй неперевірену поведінку як Спостережено. Build-и на full-page-embed мусять позначати всі твердження про iframe-bridge як Рекомендовано/Виведено. Тримай Спостережено зарезервованим для того, що саме цей конкретний build реально продемонстрував.
